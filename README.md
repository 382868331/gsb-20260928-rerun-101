# 证据审计存储底座

这是 Go 版追加式审计日志。调用方只传入项目自身生成的事件；库不扫描、不上报也不采集用户电脑活动。

## 能力

- `Append` / `AppendBatch`：按调用方提供的到达顺序写帧；每个 `source` 独立从 1 编号并维护自己的哈希链，不同来源不共享序号。
- `QuerySource`：只读取一个来源的链；`Query` 只反映文件内到达顺序，不根据事件时间或本机时间推导跨来源因果先后。
- `Seal`：封存指定来源当前完整分段，返回由调用方外部保存的 `SealSummary`，包含记录数、末尾哈希和覆盖整段的 Merkle 根。
 - `BuildRangeProof` / `VerifyRangeProof`：只向接收方披露请求序号区间、前一记录哈希和必要 Merkle 邻居；验证方可识别区间内缺号、错来源和不属于封存版本的记录。
 `VerifyRangeProofSet`：把多个独立来源各自的范围证明与各自的外部封存摘要一一配对验证；已声明来源缺证明、证明无对应摘要、重复来源都作为明确错误报告。组合验证只说明每条来源链各自完整，不把不同来源的事件时间解读成可信的全局先后。空区间（起点为 0 或终点小于起点）与越过封存段边界的区间都会被明确拒绝，落在分段中间的边界可正常验证。
- `BuildDisclosure` / `Disclosure.Narrow`：把范围证明、封存摘要和接收者授权绑定成可转交材料。收窄只能包含父材料已获准的区间；子材料保留同一封存摘要和继承的封存依据列表。`VerifyForReceiver` 同时检查授权和密码学依据，`OutsideVisibleCount` 只表示封存中存在但对该接收者隐藏的记录，不把隐藏记录报告成缺失。
- `MergeDisclosures`：只在接收者、授权名和封存依据完全相同，且两个区间相邻或重叠时合并。重叠记录通过封存记录哈希去重；重叠位置哈希不同则返回 `ErrDisclosureConflict` 并保留双方输入。不同封存即使来源名称相同也不能合并。
- `VerifySealedFile`：用外部封存摘要校验任意副本，识别改写、插入、中间删除、完整尾部删除和整段替换。
- `Open`：写入中断后只截掉物理尾部最后一条不完整帧，恢复到最后一条完整且校验通过的记录。
- `Query`：按追加/来源顺序返回记录。

## 删尾边界

文件自身只能证明现存前缀是否自洽。若攻击者从末尾完整删除一条或多条记录，被删后的文件仍可形成按来源自洽的短链；用另一个同等长度但内容不同的来源分段整段替换，也能重新算出链内哈希。因此必须把封存时的来源、记录数、末尾哈希和 Merkle 根保存在审计文件之外；校验副本或区间证明时以该外部可信摘要为准。

`SealedAt` 只是调用方的管理元数据，不参与哈希，也不能作为不同来源之间的全局先后依据。跨来源顺序只能来自事件内容或调用方明确提供、并进入哈希链的关联依据。

## 接收者可见范围

披露材料中的 `sealed_count` 是封存依据覆盖的完整记录数，`proof.start_seq` / `proof.end_seq` 是当前接收者获准查看的区间。二者之差代表授权之外的隐藏记录；验证成功只能说明可见区间真实且属于该封存，不能推断区间外记录“不存在”。验证失败时再根据缺号、哈希、Merkle 根或封存边界判断篡改。

补充材料只能合并同一封存、同一接收者和同一授权名下的相邻或重叠区间。来源名称只是事件数据的一部分；来源名相同但记录数、末尾哈希或 Merkle 根不同的摘要属于不同封存，必须分别保存和验证。
